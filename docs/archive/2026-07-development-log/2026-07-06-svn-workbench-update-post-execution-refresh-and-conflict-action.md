# SVN Workbench 更新后自动刷新与冲突入口

日期：2026-07-06

阶段：开发 -> 测试

## 背景

提交页已经具备“预览更新”和“风险感知更新确认”，但用户真正执行 `svn update` 后，页面还需要立刻回到可决策状态。

本轮补齐更新执行后的回填链路：

- 更新成功后自动重新收集提交候选。
- 候选刷新成功时，提交页列表、筛选项、默认选择状态同步更新。
- 候选刷新失败时，不再把 SVN 更新误判为失败，而是在结果面板提示“更新成功，但候选刷新失败”。
- 更新产生冲突时，在更新结果面板直接提供“打开冲突中心”按钮。

## 页面入口

提交页 -> `更新当前范围`

执行完成后，`updateResult` 结果面板展示：

- SVN 更新是否成功。
- 更新后版本号。
- 是否检测到冲突。
- 候选刷新结果。
- 冲突中心快捷入口。

## 交互细节

### 1. 更新成功且候选刷新成功

页面行为：

1. 执行 `svn update --accept postpone`。
2. 重新执行当前范围的候选收集。
3. 发送 `commitCandidatesRefreshed` 消息。
4. 前端调用现有 `applyRefreshedCandidates`。
5. 更新候选列表、筛选选项、摘要统计和默认选择。
6. 清空依赖旧候选的 AI 选择说明、拆分建议和拆分队列。
7. 更新结果面板追加 `后续: 提交候选已刷新：N 个`。

### 2. 更新成功但候选刷新失败

页面行为：

1. SVN 更新仍显示为成功。
2. 结果面板保留更新输出和版本信息。
3. 追加 `后续: 提交候选刷新失败：原因`。
4. 不覆盖当前候选列表，避免用户误以为刷新后的状态已经生效。

这个细节很重要：SVN 更新和页面刷新是两个阶段，不能因为第二阶段失败就误报第一阶段失败。

### 3. 更新成功且检测到冲突

页面行为：

1. 结果面板显示 `冲突: 是`。
2. 追加 `后续: 检测到冲突，建议进入冲突中心处理后再提交。`
3. 显示 `打开冲突中心` 按钮。
4. 点击后复用 `openConflictCenterFromCommit` 消息。
5. 进入冲突中心后，仍可使用已有 AI 冲突建议和人工决策流程。

## 安全边界

- 不自动解决冲突。
- 不自动提交。
- 不自动覆盖用户本地改动。
- 冲突仍由 `svn update --accept postpone` 保留为待处理状态。
- AI 只作为建议与辅助，不替用户做最终冲突决策。

## 核心实现

新增核心函数：

- `buildUpdateExecutionFollowUp`

扩展执行链路：

- `executeUpdateScope` 将 SVN 更新结果与后续候选刷新结果拆开处理。
- `updateExecutionResult` 消息新增候选刷新数量、刷新错误、状态刷新错误和后续动作摘要。
- `showUpdateResult` 根据后续动作摘要渲染结果面板和冲突中心按钮。

## 跨平台一致性

该能力只依赖 VS Code Webview 消息、Node.js 路径处理和 SVN CLI 输出解析。

Windows 与 macOS 的标准保持一致：

- 更新命令一致：`svn update --accept postpone`。
- 候选刷新规则一致。
- 冲突入口一致。
- 页面文案和后续动作一致。
