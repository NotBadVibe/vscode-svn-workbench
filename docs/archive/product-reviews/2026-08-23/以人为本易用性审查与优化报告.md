## 0. 结论先行

v0.0.18 已经完成并通过完整发布门禁，但“功能正确、测试通过”和“自己每天愿意用”是两件事。结合产品负责人的实际使用反馈，当前最值得解决的不是再补功能，而是把已有能力重新组织成更短、更直接、更符合人的判断顺序的工作流。

第一版报告的整体判断仍然成立：产品拥有可靠的安全底座，但能力数量、页面密度、说明文字和操作分支已经超过一次日常任务所需要的认知容量。Changes、Commit、Update、Conflicts、History、Repository 等模块分别很完整，用户却仍要自行拼接答案：

1. 我现在应该做什么？
2. 这次会影响哪里、多少文件，是否安全？
3. 我该如何比较、取舍并得到想要的最终内容？
4. 做完以后下一步是什么？

这次融合修订不推翻第一版报告的 U-01～U-14，也不把整份报告改成“冲突工具方案”。新增的重点是：**将现有差异组件提升为产品的核心交互资产**。

当前 Diff 页已经引入 `@pierre/diffs`，普通差异查看与页内编辑的视觉和操作基础明显优于冲突页。它不是待选型的新组件，而是可以继续复用的现有实现。下一阶段应优先验证并扩展它的 `UnresolvedFile`、`Editor`、自定义冲突动作、受控状态、虚拟化和 Worker 能力，让“看差异 → 就地取舍 → 手工微调 → 保存 → 验证”成为统一体验；TortoiseMerge/TortoiseSVN 用来提供成熟的交互参照，不另起一套平行渲染引擎。

整体优先级建议是：

- **第一条主线：缩短日常任务闭环。** 保留第一版对 Changes、Commit、Update、History、Repository、空态、AI 和视觉密度的系统性建议。
- **第二条主线：把差异与冲突编辑做成差异化能力。** 普通 Diff 和冲突处理共享同一套视觉语法、导航、编辑、草稿和性能策略。
- **第三条主线：用真实操作而不是功能清单验收。** 目前没有外部用户，先由产品负责人按固定任务脚本反复自测；有早期用户后再补形成性测试。

没有用户意味着可以大胆调整页面结构、入口层级和冲突工作区，不意味着可以推翻安全契约。`moduleId + taskId + operationScope`、准确预览、一次明确确认、执行前复验、草稿恢复、AI 只给建议等底座应继续保留。

最重要的产品原则是：

> 默认界面只服务当前任务；高频动作一步可达；差异直接支撑判断与修改；低频能力按需展开；安全来自准确范围和一次高质量确认，而不是堆叠控件与确认。

### 1.4 目标用户与核心任务

产品应优先服务两类人：

- **日常使用者**：知道 Update、Commit、Revert、Resolve 的大致含义，希望比命令行更省心。
- **低频 SVN 使用者**：能写代码，但不记得 SVN 术语、状态与安全边界，希望产品告诉他“现在该做什么”。

他们每天真正需要的不是 13 个模块，而是以下任务：

| 频率 | 用户任务                              | 用户心中的完成标准                                 |
| ---- | ------------------------------------- | -------------------------------------------------- |
| 很高 | 看今天改了什么                        | 快速找到文件、看 Diff、知道哪些能提交              |
| 很高 | 安全提交一组修改                      | 选对文件、写好说明、确认范围、提交完成             |
| 高   | 更新工作副本                          | 知道有没有远端变化与冲突风险，更新后能继续处理     |
| 中   | 解决冲突                              | 清楚当前冲突、保存结果、验证、标记解决、继续下一个 |
| 中   | 查历史与责任                          | 确认已加载范围，快速找到 revision、文件和作者      |
| 低   | 分支、标签、重定位、合并、属性、Patch | 需要时找得到，默认不干扰日常工作                   |
| 可选 | AI 解读、建议说明、语义拆分           | 能帮忙但不阻塞主流程，来源和数据边界可信           |

## 2. 总体诊断：功能导向强，任务导向弱

当前架构经多次迭代后形成了可靠的领域边界，但界面仍暴露了较多“系统知道什么”和“系统能做什么”，没有把它们压缩成“用户现在需要决定什么”。v0.0.17/v0.0.18 已经改善 Update、Repository、History、ScopeBar 和空状态，说明调整方向可行；剩余问题更集中在高频页面和跨页面连续性：

- Changes 同时展示共享草稿、筛选、选择摘要、文件列表、Changelist、所选提交、当前范围提交；
- Commit 同时承担选择策略、AI 选择、提交说明、AI 建议、外发说明、提交前检查、命令预览和最终确认；
- Conflicts 同时出现“AI 分析”“解释冲突意图”“本地建议”“块级采用”“保存草稿”“标记解决”；
- 普通 Diff 已有精细分栏与页内编辑，Conflicts 却仍以 marker 正文、顶部块按钮、底部建议和 Resolve 分区呈现；
- 已交付的推荐、范围栏、加载边界和分组能力仍需要在真实日常链路中验证是否真正减少了寻找与解释。

这类界面在功能演示时显得完整，在日常使用时却会产生三种成本：

1. **寻找成本**：用户先要判断应该进入哪个模块。
2. **解释成本**：进入模块后还要理解多个相近动作的差别。
3. **确认成本**：即使已经核对范围，仍可能经历复选框、预览按钮和确认对话框的连续批准。

安全与便捷不是对立项。范围准确、风险可见、一次性 token 和执行前复验属于安全；同一个意思反复让用户确认，不会显著增加安全，只会训练用户快速点击。

## 3. 问题清单与改进建议

优先级说明：

- **P0**：v0.0.18 后的下一轮应优先验证和修正；直接影响日常闭环或差异化体验。
- **P1**：在 P0 交互骨架稳定后持续打磨；影响效率、一致性或长期维护。
- **P2**：先用负责人自测和早期用户数据验证，不应抢占日常闭环资源。

### U-01 · 日常任务被拆散在多个模块中（P0）

> v0.0.18 复核：推荐下一步和独立 Update 已降低部分寻找成本，但 Changes→Diff→Commit 的连续上下文仍需按真实日常任务复核。

**问题点**

用户从 Changes 查看文件后，需要在 Changes、Diff、Commit、Changelists、Understanding 之间理解和切换。虽然会话共享选择已降低数据丢失风险，但“数据没有丢”不等于“用户没有丢失上下文”。

**怎么改**

- 建立“日常快速路径”：Changes 是起点，单击文件使用 VS Code 原生 Diff；选好文件后只有一个主操作“检查并提交 N 个文件”。
- Commit 接收选择和草稿后，默认直接落到“提交说明 + 检查结果”，不再次展示一套同等重量的选择策略；“调整文件”作为返回或展开动作。
- Changelist 与 Understanding 从日常流程的并列主动作降为“整理修改”和“需要帮助”中的按需能力。
- 不新建大首页，不改变 `moduleId + taskId + operationScope` 安全边界；只缩短已有模块的交接。

**好处**

- 降低模块选择与重复核对成本。
- 让普通提交路径先完成，高级能力仍然可达。
- 保留现有会话状态总线和范围守卫，不需要重做安全模型。

**引用案例**

[GitHub Desktop 的提交与审阅流程](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)把文件选择、Diff 和提交说明保持在同一个持续上下文；[VS Code SCM API](https://code.visualstudio.com/api/extension-guides/scm-provider)则证明了文件状态、点击 Diff、多选命令可以留在用户熟悉的原生 SCM 表面。

### U-02 · Changes 存在相互竞争且语义不够直接的提交动作（P0）

> v0.0.18 复核：保留为当前检查项；以 v0.0.18 实际按钮数量、默认选择和 payload 一致性重新走查，不直接沿用 v0.0.16 截图下结论。

**问题点**

v0.0.16 Changes 截图底部同时存在“检查并提交所选（0）”与“检查当前范围并提交（5）”。此时列表中包含冲突与 external，用户看到“已选 0”却又看到可以提交“5”，需要推理“当前范围”和“可提交候选”的差别。

**怎么改**

- 每页只保留一个主按钮。
- 未选择时主按钮写“选择要提交的文件”，不直接暗示会提交整个范围。
- 有选择时写“检查并提交 3 个文件”。
- 若当前范围内有阻止项，按钮旁只显示一句原因：“另有 1 个冲突未包含，需先处理”；提供“处理冲突”次级入口。
- “提交当前范围”放到下拉菜单，并改成准确数量：“选择 3 个可提交文件”；执行后仍停在选择阶段，不直接进入写操作。

**好处**

- 消除“0 个已选但可提交 5 个”的认知冲突。
- 主操作数量、payload 与用户可见选择保持一致。
- 降低误以为范围会被静默扩大的不信任感。

**引用案例**

[GitHub Desktop](https://github.com/desktop/desktop)以文件复选状态决定最终提交范围，并把按钮写成“Commit N files to BRANCH”；[TortoiseSVN 提交对话框](https://tortoisesvn.net/docs/release/TortoiseSVN_en/tsvn-dug-commit.html)也以勾选文件作为提交范围的直接表达。

### U-03 · 范围栏已补齐字段，但“一眼确认”仍需验证（P0）

> v0.0.18 复核：核心字段已经交付。本条转为“是否一眼看懂、是否挤占空间、在小高度与 200% 缩放下是否仍可核对”的验收项。

**问题点**

第一版审查时，ScopeBar 主要显示项目、任务和根路径 chip；文件数量、工作副本 revision、入口来源和完整范围需要通过其他区域或 Tooltip 才能拼出来。v0.0.18 已补齐这些字段，当前要验证的是用户能否在不展开详情、不依赖 Tooltip 的情况下迅速核对它们。对于 SVN 写操作，这些信息不是装饰，而是信任基础。

**怎么改**

v0.0.18 已完成核心字段；后续应按以下清单逐项做真实可见性和回归复核：

- 项目与工作副本；
- 当前任务；
- 范围摘要，例如“`src/webview/` · 3 个候选文件”；
- 工作副本 revision，例如 `r42`；
- 入口来源，例如“来自 Explorer 多选”；
- 可展开的完整范围清单，支持键盘、复制和关闭后焦点返回。

**好处**

- 用户不进入技术详情也能判断“在哪里、多少项、基于哪个 revision”。
- 过期、项目切换和 external 边界更容易被理解。
- 使安全确认更短，因为关键信息已经持续可见。

**引用案例**

[GitLens](https://github.com/gitkraken/vscode-gitlens)把 Inspect 定位为当前所选对象的上下文详情，并在同一视图中维持仓库/分支定位；本项目不照搬 Git 分支模型，只借鉴“上下文持续可见”。

### U-04 · 安全确认存在“重复批准”风险（P0）

> v0.0.18 复核：安全契约继续保留，但仍需逐项统计每个写操作从预览到执行的确认次数和重复信息。

**问题点**

Repository 高级写操作当前可能先要求勾选“我已核对命令、目标和影响”，再打开通用 Operation Intent Dialog，最后再确认一次。多重确认看起来更谨慎，实际容易形成“连续点通过”的习惯。

**怎么改**

- 同一写操作只保留一次高质量意向单确认。
- 意向单内同时展示动作、数量、范围、revision、可恢复性、命令和阻止项。
- 一般写操作不再增加前置复选框。
- 只有不可逆且对象难以恢复的极高风险操作，才使用额外的目标复述或文本输入，并且要说明为什么需要。
- 读操作、仅生成预览、打开 Diff、复制路径不弹确认。

**好处**

- 减少无效点击和“确认疲劳”。
- 用户把注意力集中在真正需要核对的内容上。
- 不削弱 token、scopeHash、candidateHash、revision 与执行前 Host 复验。

**引用案例**

[lazygit 的确认面板](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md)保持统一的 Enter 确认、Esc 取消和复制出口；其价值不在快捷键本身，而在所有危险动作共用一个稳定确认模型。

### U-05 · Update 已完成拆分，闭环仍需围绕“结果”验证（P0）

> v0.0.18 复核：独立 Update、结果冲突数量和直达 CTA 已交付；后续只优化完成后的决策路径和反馈，不重复拆模块。

**问题点**

v0.0.17 已把 Update 从 Repository 拆成独立模块并增加结果冲突 CTA。现在需要核对的不是“有没有独立页面”，而是用户是否仍要经历“进入页面—重新检查—看数字—确认—再理解下一步”，以及完成后能否自然进入正确冲突或修改上下文。

**怎么改**

独立 Update 页只保留三个状态：

1. **未检查**：主操作“检查远端更新”。
2. **已检查**：显示本地修改、远端修改、重叠路径和风险；主操作“更新当前范围”。
3. **已完成**：显示新增/修改/删除/冲突数量；有冲突时主操作立即变为“处理 N 个冲突”，无冲突时变为“查看更新后的修改”或“返回编辑”。

进度阶段使用“连接仓库 → 检查远端 → 合并到工作副本 → 刷新状态”，允许取消，并明确取消后会重新采集状态。

**好处**

- Update 不再只是一个命令预览页，而是一个完成后有出口的任务。
- 冲突处理入口紧贴结果，不需要用户回忆模块名称。
- 与当前 v0.0.18 的 `UpdateSnapshot.conflicts` 和结果页冲突 CTA 保持一致。

**引用案例**

[TortoiseSVN Update](https://tortoisesvn.net/docs/release/TortoiseSVN_en/tsvn-dug-update.html)在完成页汇总 updated/added/removed/conflicted 数量，并允许从冲突条目直接进入合并工具；这是 SVN 场景最直接的可复用案例。

### U-06 · 冲突页的帮助入口多于用户当前需要的决定（P0）

> v0.0.18 复核：入口闭环已有改善，但 Diff 与 Conflicts 使用两套内容呈现，冲突块取舍、手工微调和结果确认仍未形成一个连贯工作区。详见第 6 节。

**问题点**

当前冲突页同时提供“AI 分析”“解释冲突意图”、块级“采用我的/对方/保留两者”、本地合并建议、草稿保存与 Resolve。用户需要先理解多个建议来源，再判断自己是否已经保存、是否可以标记解决。

**怎么改**

把页面固定成一条可见流程：

```text
选择冲突文件 → 处理冲突块 → 保存工作副本 → 运行/查看验证建议 → 标记解决 → 下一个冲突
```

- 顶部只显示进度：“剩余 1/2 个冲突”。
- 默认工作区聚焦当前冲突与合并结果；“我的修改/对方修改/BASE”作为辅助 Tab。
- “AI 分析”和“解释冲突意图”合并为一个“需要帮助”入口，展开后再选择“本地建议”或“模型解释”。
- Resolve 按钮前显示检查清单：冲突标记已清除、已保存、文件仍在范围内；无法自动验证的项目明确写“需人工确认”。
- Resolve 成功后自动选中下一个未解决冲突；全部完成后给“返回 Update 结果/查看本地修改”。

**好处**

- 用户始终知道自己在冲突流程的哪一步。
- AI 从主任务竞争者变成按需帮助。
- 减少“保存内容”和“标记解决”两个概念混淆。

**引用案例**

[TortoiseSVN 合并冲突说明](https://tortoisesvn.net/docs/release/TortoiseSVN_en/tsvn-dug-merge.html)明确区分 Edit、保存和 Mark as resolved，并只在满足条件后启用标记解决；[GitButler 冲突流程](https://github.com/gitbutlerapp/gitbutler/blob/master/crates/but/skill/references/reference.md)也把 resolve status、编辑和 finish 组织为连续步骤。二者都说明“进度顺序”比同时展示更多工具更重要。

### U-07 · AI 在多个页面占据与确定性任务同等的视觉权重（P0）

> v0.0.18 复核：AI 仍应是可选辅助；在冲突页尤其应服从“比较—修改—保存—验证”的主流程。

**问题点**

Commit、Changelists、Conflicts、Understanding 都有模型相关按钮、外发说明、建议来源和证据区。透明说明是必要的，但当 AI 与本地规则、提交、保存、Resolve 同时处于首屏，用户会把时间花在判断“要不要用 AI”，而不是完成 SVN 任务。

**怎么改**

- AI 统一放入“需要帮助”或“生成建议”区域，默认折叠；核心 SVN 动作不依赖展开。
- 本地规则自动运行并以内联状态呈现，不使用“智能”“AI”字样。
- 用户主动选择模型能力后，才展示模型、预算、外发范围与回执。
- 同一页面最多一个模型入口；例如冲突页不同时出现“AI 分析”和“解释冲突意图”。
- AI 建议采用后仍回到任务主流程，不让建议卡长期占据首屏。

**好处**

- AI 仍然可信、可控，但不会把产品变成模型配置器。
- 未配置模型时界面更干净，核心 SVN 流程更像完整产品而非降级模式。
- 降低用户对“是否必须把代码发给模型”的焦虑。

**引用案例**

[GitHub Desktop](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)把生成提交说明作为 Summary 附近的可选动作，手写与提交主流程始终存在；[GitButler Commit Editing](https://docs.gitbutler.com/features/branch-management/commits)也把生成信息放在开始提交后的编辑上下文中，而不是独立要求用户先进入 AI 模块。

### U-10 · 空状态矩阵已补齐，仍需扩展到全局恢复体验（P1）

> v0.0.18 复核：Changes、Commit、Update 已完成空状态矩阵；继续将同一标准覆盖 Diff、Conflicts、History 和错误恢复。

**问题点**

v0.0.15 已让 Diagnostics 动作可执行，v0.0.17 又补齐 Changes、Commit、Update 的空状态矩阵，这是正确改进。但 Diff、Conflicts、History、设置与错误恢复仍需统一检查；非 SVN 文件夹、干净工作副本、筛选为空、尚未加载和加载失败必须保持可区分的原因与下一步。

**怎么改**

所有空态遵守三句话：

1. 发生了什么；
2. 这是否正常；
3. 现在可以做什么。

**好处**

- 新用户不需要通过错误页学习产品模块。
- 降低空态与故障状态混淆。
- 恢复动作可直接用于 E2E 验收。

**引用案例**

[VS Code Welcome Views 指南](https://code.visualstudio.com/api/ux-guidelines/views)建议空态内容短、按钮只用于主动作、链接文字直接说明目的；这正适合本项目的空态矩阵。

- 测试时不给模块名称提示，只给任务目标。
- 记录任务完成率、首次停顿点、返回次数、误选动作、完成时间和任务后信心评分。
- 自动化继续证明安全与状态正确；真人走查证明入口、文案和顺序可理解，两者不能互相替代。

**好处**

- 避免继续用更多说明弥补结构问题。
- 让“以人为本、便捷为本”成为可验收目标，而非主观口号。

## 4. 建议的目标信息架构

### 4.1 双速工作台

不建议再建大首页，也不建议把所有复杂能力强塞回原生 SCM。更适合本项目的是“双速工作台”：

```text
快速路径（高频、低解释成本）
Explorer / 编辑器 / 原生 SCM
  ├─ 看状态与 Diff
  ├─ 选择文件
  ├─ 打开 Changes / Update / Commit / Conflicts
  └─ 执行简单只读动作

深度任务（复杂、需要范围与证据）
Svelte 独立任务窗口
  ├─ 提交检查与最终确认
  ├─ Update 风险与结果
  ├─ 冲突编辑与 Resolve
  ├─ History 详情与恢复
  └─ Repository 高级操作、AI 回执与证据
```

这不是新建平行业务 UI：原生 SCM 已经存在，Svelte 仍是复杂业务界面的唯一实现。调整的是“什么任务应该在哪个表面完成”。

### 4.2 日常任务优先级

全局只按以下顺序提升动作：

1. 有冲突：处理冲突。
2. 工作副本需要恢复：进入 Cleanup/恢复。
3. 有可提交修改：查看/提交修改。
4. 工作副本干净：检查远端更新。
5. 没有阻塞：查看历史或继续编辑。

推荐必须高置信、可解释、可忽略，不持久惩罚用户。不要在每个模块永久显示一条“推荐下一步”大横幅；只有冲突、锁定、过期等强状态使用全宽 notice，普通推荐放在 ScopeBar 下的一行 Task Summary 或主按钮文案中。

### 4.3 标准页面骨架

每个任务只使用以下五层：

```text
ScopeBar：在哪里 / 什么范围 / 哪个 revision
Task Summary：当前状态 / 为什么 / 下一步
Task Body：完成当前任务所需的列表、Diff 或表单
Primary Action：唯一主动作 + 必要的次级动作
Result：发生了什么 / 下一步 / 恢复入口
```

设置、证据、命令、模型预算、完整路径等信息按需展开，不与主任务争夺首屏。

## 5. 各模块建议方案

### 5.1 Changes：从“综合控制台”改为“今天改了什么”

**保留**

- 搜索、状态筛选、排序、密度、键盘多选、路径详情、窗口化、external/blocked 标识。

**调整**

- 默认折叠共享提交草稿；只有已有草稿时显示一行摘要“已有提交草稿，继续编辑”。
- 顶部工具条收敛为搜索、状态、更多筛选；选择摘要仅在产生选择后出现。
- 双击或 Enter 打开原生 Diff；行尾最多保留 1 个常用动作，其余进入菜单。
- Sticky 底栏只保留“检查并提交 N 个文件”主按钮和“整理到变更集”次级动作。
- 冲突行直接提供“处理冲突”，不允许进入提交选择。
- 5000 文件时默认按目录分组或提供树/平铺切换；显示“已加载 5000，当前筛选 N”，避免仅靠长列表。

**预期结果**

用户进入后 3 秒内能回答：有几个可提交文件、有没有冲突、下一步按钮是什么。

### 5.2 Commit：从“所有选择与 AI 能力集合”改为“提交最后一公里”

**保留**

- 精确候选、草稿保护、团队规则、受限差异回执、建议不覆盖草稿、提交前远端检查、意向单。

**调整**

- 默认两段：上方紧凑的“3 个文件待提交”摘要，下方提交说明与检查结果。
- 文件选择默认折叠；点击“调整文件”才展开完整列表。
- “应用本地规则”自动完成并展示结果，不作为首屏按钮。
- “获取 AI 建议”改为提交说明旁的魔法棒次级动作；外发回执仅在点击后出现。
- 提交前检查自动在选择或草稿稳定 300–500ms 后执行；“重新检查”只在过期/失败时出现。
- 最终按钮始终写明仓库/项目语义和数量：“提交 3 个文件”。
- Operation Intent Dialog 只在真正执行前出现一次。

**预期结果**

从 Changes 带入选择后，用户只需要核对文件摘要、写说明、确认一次。

### 5.3 Update：独立、短、结果驱动

v0.0.17 已按 U-05 方向完成独立 Update。后续不重复拆分，重点复核三状态是否清楚、结果是否一步通向冲突或后续修改，并继续避免在 Update 页混入仓库高级任务。

### 5.4 Conflicts：按步骤推进，不让来源争夺注意力

按 U-06 重排，并采用第 6 节的 `@pierre/diffs` 优先方案。建议增加 `ConflictStepBar`，将“是否保存”“是否仍有冲突标记”“是否可 Resolve”做成可核对状态，而不是继续增加说明卡片。

### 5.5 Changelists：以“任务分组”而非“AI 功能”开场

- 左侧“未分组修改”，右侧“任务组”；选中文件后可拖放或点击“移动到…”。
- 默认本地按目录/类型建议只作为轻量“自动整理”入口。
- “按改动意图拆分（含差异需确认）”放入“更多整理方式”，主动选择后再展示 AI 回执。
- 组卡标题直接可编辑；应用前只确认实际变更的 Changelist 操作。

[TortoiseSVN Changelists](https://tortoisesvn.net/docs/release/TortoiseSVN_en/tsvn-dug-changelists.html)证明了在修改检查和提交表面直接分组、拖放、按组选择，比另开一个抽象“分组建议”流程更贴近日常心智；[GitButler Parallel Branches](https://docs.gitbutler.com/features/branch-management/virtual-branches)的 lane 与拖放可作为视觉参考，但不能照搬其 Git 虚拟分支语义。

### 5.6 History：明确加载边界，保留选择上下文

v0.0.18 已交付 U-09 的加载边界和查询能力。后续复核大仓库中的等待反馈与选择保持；搜索、比较和恢复仍属于同一任务，但“恢复”是写操作，必须保持准确预览与确认契约。

### 5.7 Repository：分组与渐进展开

v0.0.17 已按 U-08 完成分组与渐进展开。后续只做命名、默认展开和查找效率复核；Repository 默认入口仍应是 Browse，Relocate 等危险项不得自动提升为全局主动作。

### 5.8 Diagnostics 与首次使用：恢复优先于教学

- 启动失败时直接显示最可能的一个主动作，例如“选择 SVN 可执行文件”。
- 成功后不要求用户先学习所有模块，只给“查看本地修改”。
- v0.0.18 已交付三分钟引导；后续必须随着真实页面重构同步更新，并继续在最终确认前结束。
- 引导可以跳过、重开，不用弹窗阻塞每次启动。

### 5.9 Settings 与 Activity：不进入日常主导航

- Settings 只从齿轮、错误恢复和相关功能入口打开。
- Activity 在操作完成通知和“更多”中可达；只有发生失败或存在恢复动作时提升入口。
- AI、团队规则、SVN 安全继续分 Tab，但首屏只解释当前状态和一个主动作，不重复大段产品说明。


## 6. 差异审阅与冲突编辑补充方案：复用现有 `@pierre/diffs`

### 6.1 本次补充的定位与技术决策

本节是第一版综合易用性报告的补充，不取代 U-01～U-14，也不要求把产品全部改造成差异工具。

技术决策应明确为：

> 以现有 `@pierre/diffs` 适配层作为普通 Diff 和冲突编辑的首选渲染/编辑底座；先验证并扩展组件已经提供的能力，不另起一套 CodeMirror 三方差异引擎。TortoiseMerge 用于借鉴成熟交互，不用于照搬 Windows 外观。

理由有三点：

1. 当前 Diff 页已经证明该组件可以在严格 CSP、VS Code 主题、Svelte 生命周期和 Host 快照下稳定工作。
2. 已安装包不只有 `FileDiff`；还导出了 `UnresolvedFile`、`Editor`、自定义冲突动作、`resolveConflict`/`resolveRegion`、`VirtualizedFileDiff`、`ScrollSyncManager` 和 Worker 支持。
3. 普通 Diff 视觉已经较成熟，最大收益来自把这套语言延伸到冲突场景，而不是重新解决语法高亮、行号、折叠、主题、编辑和性能问题。

### 6.2 已有资产审计

| 编号 | 问题点 | 怎么改 | 好处 | 引用案例 |
| --- | --- | --- | --- | --- |

| D-05 | 块级自动取舍之后，用户仍需手工改变量名、逗号、顺序或组合逻辑 | 结果区保持可编辑；块级动作只是可撤销编辑，动作后光标进入结果位置，并提供撤销/重做和查找 | 不把冲突解决误导成简单二选一；自动动作与人工判断连续 | `@pierre/diffs/edit` 已提供编辑历史、状态和程序化编辑 API |

### 6.4 目标冲突工作区

首版目标不是一次做出完整 IDE，而是让最常用决定集中在一个稳定视口：

```text
顶部：src/foo.ts · 冲突 2/7 · r41 ↔ r42
      [上一个冲突] [下一个冲突] [显示选项] [在外部工具打开]

来源与角色：我的修改（本地） | 对方修改（仓库 r42） | BASE
当前冲突：
  差异内容……
  [采用我的] [采用对方] [先我的后对方] [先对方后我的]

合并结果（可编辑）：
  使用与普通 Diff 相同的语法高亮、行号、查找、撤销/重做
  冲突块动作产生的变化立即体现在结果中并可撤销

底部状态：
  未保存 / 已保存 · 剩余 1 个 marker · 验证未运行
  [保存合并结果] [运行验证] [使用当前工作副本内容并标记解决]
```

交互细节：

- 打开文件后自动聚焦第一个未解决块；`Alt/Option+↑/↓` 或与现有 Diff 一致的快捷键切换冲突块。
- 每次块级采用都是普通、可撤销的编辑，不直接写入工作副本。
- 保存只更新草稿/工作副本内容；Resolve 仍是独立写操作，继续使用当前预览、确认令牌和执行前复验。
- 切换文件、刷新快照或关闭窗口时，沿用现有草稿三选一保护；旧 hash、旧 revision 或旧 scope 下的结果必须失效。
- 小高度下让“合并结果”拥有明确滚动区，顶部与底部保持紧凑 sticky；不得用全局 `overflow` 掩盖布局。
- 所有状态同时使用文字和图标，不只依靠红/绿背景。

### 6.5 Pierre-first 实现方案

#### 阶段 A：能力验证，不改 Host 契约

建立一个只使用 fixture 的 Svelte spike，验证安装版本 `@pierre/diffs@1.3.4` 的真实行为：

1. `UnresolvedFile` 能否在现有 CSP shim 和 Shadow DOM 观察器下正确挂载、清理和切换主题。
2. 自定义 `mergeConflictActionsType` 是否能渲染中文按钮、键盘焦点和可访问名称。
3. `onMergeConflictAction` 受控模式下是否能把每次选择上报给 Svelte 状态，而不让库成为业务主权威。
4. `Editor` 是否可稳定附加到冲突结果，保留撤销/重做、光标、选区和 Host 快照刷新后的编辑状态。
5. 组件对 CRLF、无末尾换行、二进制/超长行、嵌套或损坏 marker 的行为。
6. 普通 Diff 现有 fallback 在新适配器中是否仍可用。

`UnresolvedFile` 和编辑能力在官方文档中属于仍在演进的能力，因此先 spike、再接生产；不要先升级依赖来追新 API，也不要把内部未声明接口写进业务代码。

#### 阶段 B：建立冲突适配器

建议新增 `src/webview/features/conflicts/ConflictDiffView.svelte`，职责严格收窄：

- 输入：稳定文件 identity、语言、含 marker 的工作文本、角色映射、只读/编辑模式。
- 输出：当前文本、脏状态、光标/冲突块位置和用户选择的语义动作。
- 渲染：`UnresolvedFile` + 自定义就地动作；失败时通知父层回退。
- 生命周期：复用或抽象 `DiffView.svelte` 的挂载、清理、CSP observer、主题、高亮预热和编辑态不重建策略。
- 禁止：直接发送 Resolve、扩大 scope、信任组件返回路径、绕过 Host token。

冲突领域状态仍由 Svelte/Host 管理。库的 `MergeConflictResolution` 只提供 `current | incoming | both`；SVN 适配层必须根据实际 marker 生成顺序映射 Mine/Theirs。反向“两者都要”、恢复原块、删除两侧、手工组合等动作作为受控编辑实现，并进入同一撤销栈。

#### 阶段 C：统一普通 Diff 与冲突编辑控制器

把以下能力抽成共享的小型领域模块，不把两个巨型页面硬合并：

- 上一个/下一个变更或冲突；
- 当前行/块聚焦；
- 脏状态、自动检查点、保存、导出和放弃；
- 编辑器 API：`getText`、`focusLine`、`applyRegionEdit`、undo/redo；
- 视图偏好：split/unified、展开上下文、空白策略；
- 失败降级与遥测事件。

普通 Diff 继续使用 `FileDiff`；冲突使用 `UnresolvedFile`。共享的是适配和任务行为，不是强迫两个组件具备完全相同的数据模型。

#### 阶段 D：按证据增加高级布局

只有在单视口方案完成并通过性能/任务验收后，再考虑：

- Mine vs BASE、Theirs vs BASE 两个只读 `FileDiff` 与可编辑结果同步滚动；
- TortoiseMerge 式 overview/locator；
- 行内接受/拒绝和多选冲突块批处理；
- 针对超大文件的专门窗口化冲突视图。

这一步可以借助 `ScrollSyncManager`、`CodeViewCoordinator` 或多个 `FileDiff` 实例，但必须先验证其在 VS Code Webview 中的焦点、滚动和内存成本。不要为了看起来像 TortoiseMerge，第一天就固定成四窗格。

### 6.6 性能策略：相信方向，但只用实测下结论

现有组件具备支持良好性能的条件：CSS Grid/Shadow DOM 渲染、Shiki 懒加载、`VirtualizedFileDiff`、Worker Pool、纯文本先显示再高亮等能力。当前普通 Diff 也已经使用语言预热和实例保持策略。因此“继续使用它”是合理方向。

但要区分三件事：

- `VirtualizedFileDiff` 已导出，不代表 `UnresolvedFile` 自动拥有等价的虚拟化版本；当前包没有单独导出的 `VirtualizedUnresolvedFile`。
- 普通只读 Diff 快，不代表带编辑、marker 解析、自定义动作和持续状态同步的冲突视图同样快。
- 小 fixture 流畅，不代表 5000 行、500 个冲突块、超长行和频繁保存回执仍流畅。

建议建立专项矩阵：

| 场景 | 数据档位 | 重点测量 | 候选门槛 |
| --- | --- | --- | --- |
| 普通 Diff | 100、1000、5000、10000 行；小/中/大变更比例 | 首屏、完整高亮、滚动、切换文件、内存 | 5000 行首个可见内容 P95 ≤ 800ms；交互后不连续阻塞 |
| 冲突文件 | 10、100、500 个冲突块；1000、5000、10000 行 | marker 解析、首个冲突定位、块级采用、重新渲染 | 100 块首个可操作冲突 P95 ≤ 1000ms；块动作反馈 ≤ 100ms |
| 编辑 | 连续输入、粘贴 1000 行、撤销/重做、程序化采用 | 输入延迟、光标保持、撤销等价性 | 普通输入处理 P95 ≤ 50ms；不得因 Host 回执丢失输入 |
| 高亮 | text、TS、JSON、XML、超长行 | 主线程长任务、Worker 命中、渐进高亮 | 首屏不等待高亮；输入期间不执行 >50ms 的高亮长任务 |
| 生命周期 | 连续切换 100 个文件、主题切换、关闭重开 | 实例/observer 清理、内存回落、焦点 | 无持续增长；编辑草稿和选择按 identity 恢复 |
| 可访问布局 | 720×480、200%、Light/Dark/High Contrast | 可达性、滚动归属、sticky 遮挡 | 所有动作可键盘完成，状态不只靠颜色 |

这些数值是首轮候选预算，不是对当前组件的既成结论。应在项目支持的 Node/VS Code 和至少一台中低配设备上先取得 baseline，再根据真实任务调整阈值。

性能落地顺序：

1. 首个可见内容优先，语法高亮允许稍后补齐。
2. 普通大 Diff 评估切到 `VirtualizedFileDiff` 和 `@pierre/diffs/worker`。
3. 冲突视图先测 `UnresolvedFile`；若大文件无法满足预算，按阈值关闭高亮、缩短上下文或切到外部/原生合并工具。
4. 只保留一个可编辑实例；Mine/Theirs/BASE 优先按需挂载只读视图。
5. 文件切换前释放实例、observer 和 Worker 任务；缓存以稳定 identity 和内容 hash 为键，不以路径字符串盲目复用。
6. 将性能测试加入现有 `scripts/measure-webview-performance.js` 或独立 fixture，但不修改已发布 evidence。

### 6.7 TortoiseSVN/TortoiseMerge 值得融入的细节

| 习惯 | 融入方式 | 本项目适配 |
| --- | --- | --- |
| Mine/Theirs/BASE 角色持续可见 | 标题、revision 和来源固定显示 | 使用中文优先术语，并保留 Mine/Theirs 作为辅助，不暴露模糊的 current/incoming |
| 上一个/下一个差异与冲突 | 复用当前 Diff 导航，冲突页使用相同位置和快捷键 | 数量来自当前文件且与左侧文件进度分开 |
| Use mine/theirs/both | 就地中文动作；两种 both 顺序都提供 | 动作只编辑草稿，不能直接 Resolve |
| 可编辑合并结果 | 冲突取舍后直接人工微调 | 复用 Pierre `Editor`，纳入撤销栈和草稿检查点 |
| 空白比较选项 | “显示设置”中提供忽略/显示空白 | 只改变比较呈现时要明确说明，不静默改内容 |
| Overview/locator | 大文件时显示冲突位置和当前视口 | 作为后续增强，先证明性能和键盘可达 |
| 外部工具 | 保留“在 TortoiseMerge/配置的合并工具中打开” | 作为可选出口与大文件降级，不作为核心流程前提 |

不照搬的部分包括 Windows 菜单样式、过密工具栏、仅靠红绿表达状态和一次性塞入四个窗格。要借的是成熟判断路径，不是外观。

### 6.8 安全、数据与失败边界

- `@pierre/diffs` 只处理已经通过 Host 范围校验的文本，不决定文件是否可以保存或 Resolve。
- 组件回调中的文件名、冲突索引和文本都要重新绑定当前 `moduleId + taskId + operationScope`、identity、candidate hash 和 revision。
- 块级采用、AI 建议和程序化编辑都只是草稿变化；写入工作副本前重新核对文件仍在候选集合。
- 保存后如果 SVN 状态、revision 或 marker 变化，旧冲突动作和 AI 结果立即失效。
- 组件异常时保留当前草稿，明确告知“差异视图加载失败，可切换简化编辑器或外部工具”，并记录可诊断原因。
- 二进制、不可解码、超预算、损坏 marker 和属性冲突必须有专门分支，不强行进入文本合并视图。
- Resolve 继续展示准确命令预览和影响数量，并由用户明确确认；AI 或组件不得自动执行。

### 6.9 验收任务

在没有外部用户的阶段，由产品负责人每次候选构建固定完成以下任务并录像或记录：

1. 打开一个双向修改的 TypeScript 冲突，5 秒内指出 Mine、Theirs、BASE 和最终结果。
2. 连续完成“采用我的”“采用对方”“两种保留顺序”，并各自撤销一次。
3. 采用一侧后手工修改同一块，保存、关闭、重开，内容和光标附近位置不丢失。
4. 在 100 个冲突块中跳到指定块，切换空白显示，再回到原块。
5. 修改保存后触发外部文件变化，确认旧草稿/旧结果不会静默覆盖新内容。
6. 在 AI 未配置、AI 超时和 AI 返回范围外路径时，仍能完整人工解决。
7. 在 720×480、200% 缩放、Light/Dark/High Contrast 下只用键盘完成一个冲突。
8. 用 5000/10000 行 fixture 验证第 6.6 节预算和大文件降级。

通过标准不是“按钮都能点”，而是用户能持续回答：我正在比较谁、这次动作改了什么、是否已保存、为什么现在能或不能 Resolve。

### 6.10 明确不做

- 不把第一版综合易用性报告替换成单一 Diff/Conflict 报告。
- 不重新实现语法高亮、Diff 算法或一套平行 CodeMirror 三方引擎。
- 不在能力 spike 前大范围改协议、Host 或安全状态机。
- 不默认升级 `@pierre/diffs`；先以锁定安装版本验证，再单独评估升级。
- 不把“组件看起来很快”写成性能结论；必须保留 baseline、数据规模和设备条件。
- 不要求所有冲突都在内置界面解决；专家外部工具和超大文件降级继续存在。

## 8. v0.0.18 后续重构路线

v0.0.17 和 v0.0.18 已经发布，不能再把建议写成对这两个版本的排期。当前没有外部用户，可以重排页面和交互，但应以小步可回退的任务切片实施，不对已发布记录或安全底座做历史改写。

### 8.1 第 0 阶段：建立负责人自用基线

用同一份隔离 SVN 工作副本连续完成第 10.1 节任务，记录：

- 从进入产品到找到主动作的时间；
- 每个任务经过的页面、点击数、返回次数和确认次数；
- 哪些文案需要停下来推理；
- Diff/冲突中的输入延迟、滚动卡顿和上下文丢失；
- 哪些信息真实帮助决定，哪些只是占空间。

同时保留 v0.0.18 截图和测量结果作为 before 基线。没有基线就直接重做，容易把“个人记忆中的不顺”变成新的主观设计。

### 8.2 第 1 阶段（P0）：差异化冲突工作区 + 日常闭环

| 批次 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A | 第 6.5 节 Pierre 能力 spike | `UnresolvedFile`、自定义动作、编辑、CSP、主题、生命周期和性能结论都有 fixture 证据 |
| B | 冲突内容改为 Pierre-first | 当前块就地取舍、可编辑结果、撤销/重做、草稿保护和安全降级完整 |
| C | Changes→Diff→Commit 连续上下文 | 文件、选择、滚动位置和草稿不重复丢失；每页只有一个清楚的主动作 |
| D | 冲突完成路径 | 保存、验证、Resolve、下一个冲突的顺序持续可见；Update/Changes 来路可回到正确结果 |
| E | 自用回归 | 第 6.9 和 10.1 节任务全部完成，记录至少一轮基于停顿点的修正 |

这里允许推翻冲突页布局和普通 Diff 工具条组织，但不推翻 Host 权威状态、scope/token/revision 复验和 Resolve 独立确认。

### 8.3 第 2 阶段（P1）：整体细节与一致性

1. 收敛 Commit、Changes、Conflicts 中竞争的按钮和说明卡片。
2. 将 AI 统一为按需帮助，不占据确定性 SVN 主流程。
3. 统一 Task Summary、Primary Action、空态、错误恢复、Tooltip、快捷帮助和焦点返回。
4. 复核已交付的 ScopeBar、History、Repository 分组、Update 结果和三分钟引导，而不是重复实现。
5. 在 720×480、200%、Light/Dark/High Contrast 和中文 IME 下逐页人工验收。
6. 随体验切片拆分巨型组件，优先共享 Diff/冲突控制器与 `AssistancePanel`，不做无关格式化或全仓重构。

### 8.4 第 3 阶段（P2）：用证据决定高级能力

只有前两阶段稳定后，再根据负责人高频使用和早期用户反馈决定：

- 多窗格同步比较、overview/locator；
- 冲突块批处理和更丰富的行级取舍；
- 筛选预设跨会话持久化；
- 高度可配置布局；
- 更深的原生 SCM 融合；
- 新的 AI 差异解释能力。

### 8.5 暂不建议投入

- 新的大首页或更多一级模块；
- 把 TortoiseMerge 外观逐像素搬进 VS Code；
- 为每个任务增加独立 AI 按钮；
- 用教程解释仍然复杂的页面；
- 没有测量依据的组件替换或依赖升级；
- 对 SVN 不具备可靠恢复语义的“一键撤销”承诺；
- 为追求视觉效果牺牲小高度、键盘、IME、高对比度或明确滚动归属。

## 10. 验收指标：把“好用”变成可检查结果

### 10.1 形成性用户任务

阶段 A 由产品负责人在固定隔离工作副本中重复执行；阶段 B 在出现早期用户后邀请 3–5 名用过 SVN、未使用过 SVN Workbench 的开发者。每人完成：

1. 首次打开非 SVN 文件夹，恢复到可查看一个工作副本修改。
2. 从 Explorer 选中一个目录，找到 3 个可提交文件并查看其中 1 个 Diff。
3. 排除生成物，写提交说明，走到最终确认前，不执行真实提交。
4. 检查远端更新并执行到隔离测试工作副本；更新产生冲突后进入正确冲突文件。
5. 编辑冲突、保存、标记解决并进入下一个冲突。
6. 查找指定作者/日期的较早 revision，并确认是否已加载完整范围。
7. 在 AI 未配置状态下重复核心提交准备流程。
8. 在 5000 文件数据集查找、筛选并选中指定文件。

### 10.2 建议指标

| 指标            | v0.0.18 后续候选目标                           | 说明                           |
| --------------- | --------------------------------------------- | ------------------------------ |
| 首次任务成功率  | 早期用户中 ≥80% 无口头提示完成前 5 个任务     | 形成性目标，不宣称统计显著     |
| 日常路径成功率  | 5/5 用户完成“看 Diff → 到提交确认前”          | 任何范围扩大都为阻断失败       |
| 主动作定位时间  | 中位数 ≤10 秒                                 | 从页面稳定显示开始计时         |
| 提交准备决策点  | 从 Changes 到意向单不超过 3 次主要决定        | 搜索、输入文字不计为决策点     |
| 写操作确认次数  | 每个操作 1 次意向单确认                       | 预览生成不算确认               |
| Update 冲突转入 | 1 次动作进入正确 Conflicts scope              | 数量与路径一致                 |
| 任务后信心评分  | 7 分制中位数 ≥5                               | 问“我确信这次只会影响预期文件” |
| 关键停顿        | 同一文案/控件不得使 2 名以上用户停顿 >10 秒   | 出现即进入修正文案或结构清单   |
| 安全契约        | 现有 scope/token/revision/AI/凭据门禁全部通过 | 易用性不能以降低安全换取       |

### 10.3 自动化与人工验收分工

- 单元/组件/Extension Host：证明范围、状态、token、失败与恢复分支正确。
- Webview E2E：证明主路径、焦点、IME、滚动和动作数量一致。
- 视觉回归：证明三主题、三尺寸与 200% 缩放没有信息层级退化。
- 真人走查：证明用户能找到入口、理解文案、完成任务。
- 真实 SVN：证明 Update/Conflict/Commit 的结果和恢复路径符合实际工作副本。

不得用自动化测试、axe 或截图替代真人走查，也不得用用户“最终完成了”掩盖长时间停顿和反复返回。

## 11. 风险与控制

| 风险                            | 可能后果                          | 控制方式                                            |
| ------------------------------- | --------------------------------- | --------------------------------------------------- |
| 简化时隐藏了专家能力            | 老用户认为功能退化                | 只降级到“更多/高级”，不删除；提供命令面板直达       |
| 自动预选造成范围误解            | 用户担心静默扩大                  | 默认仅建议，不自动新增；数量与文件列表持续一致      |
| Native SCM 与 Svelte 状态不一致 | 两处显示不同选择或草稿            | 继续以 Host session 为权威，Webview 不伪造 identity |
| 推荐下一步判断错误              | 用户被带到错误任务                | 只对冲突/锁定/过期等确定状态强推荐；允许忽略        |
| AI 折叠后使用率下降             | 可选增强不易发现                  | 在相关输入旁保留单一入口；不做全局广告              |
| 页面拆组件引入回归              | 状态或焦点丢失                    | 伴随体验批次小步提取；组件/E2E 覆盖焦点与草稿       |
| 参考 Git 产品过度               | 引入 SVN 不存在的 stage/undo 心智 | 每条案例明确只借交互模式，领域语义由 SVN 契约决定   |


## 12. 最终建议排序

如果下一轮只能做五件事，按以下顺序：

1. 以现有 `@pierre/diffs` 做第 6 节能力 spike，并把冲突页改造成“就地比较、取舍、微调、保存”的统一工作区。
2. 用固定自测脚本重走 Changes → Diff → Commit、Update → Conflicts 两条高频链路，删除竞争主动作和重复上下文。
3. 保留并复核 ScopeBar、准确数量、revision、草稿、一次确认和执行前复验，让大胆重构不降低安全信任。
4. 将 AI、来源说明和高级设置收进按需帮助，集中打磨焦点、滚动、快捷键、空态、中文 IME、小高度和高对比度细节。
5. 用性能矩阵和任务停顿数据决定多窗格、locator、虚拟化阈值与下一轮范围，不再按功能数量推进。

完成后，SVN Workbench 的核心竞争力应更清晰：它不只是“功能很多的 SVN 页面集合”，而是“在 VS Code 里用可靠、快速、可编辑的差异上下文，让复杂 SVN 操作更确定、更省心的工作台”。
