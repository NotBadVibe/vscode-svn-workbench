# SVN Workbench 文档中心

> 文档身份：`documentation-index`
>
> 适用对象：开发者、评审者与检索仓库资料的 AI。
>
> 机器索引：[`catalog.json`](./catalog.json)。

## 1. 只保留三类文档

| 区域                       | 身份     | 权威性     | 用途                                   |
| -------------------------- | -------- | ---------- | -------------------------------------- |
| [`current/`](./current/)   | 当前基线 | 当前规范   | 产品范围、交互约束、实现映射和测试门禁 |
| [`releases/`](./releases/) | 版本记录 | 版本内有效 | 已发布事实、开发中版本计划、候选及证据 |
| [`archive/`](./archive/)   | 历史归档 | 非当前权威 | 追溯旧规格、原型、里程碑和内部候选     |

不得在 `docs/` 根目录新增临时报告、PASS 记录、日期计划或单功能总结。内容必须归入上述三类之一；没有长期检索价值的过程记录放到任务、Issue、PR 或 `.validation/evidence/`，不进入文档树。

## 3. AI 检索顺序

AI 回答仓库问题时必须先判断问题类型，再按固定顺序取证。

### 当前行为或开发约束

1. 实际源码、协议类型和自动化测试；
2. [`current/README.md`](./current/README.md)；
3. 对应 current 基线；
4. 开发中版本计划，仅用于解释尚未进入当前基线的目标。

不得使用 archive 或旧 release 计划覆盖当前代码与测试。

### 已发布版本事实

1. [`releases/README.md`](./releases/README.md)；
2. 对应版本 `manifest.json`；
3. 对应版本 `README.md`；
4. manifest 指向的 accepted evidence。

已发布版本目录不可因整理、去重或修正文案而改写。

### 未来计划

1. `catalog.json` 中 `phase=developing|planned` 的版本；
2. 对应版本 README；
3. 明确标注“已完成”“待实施”“候选门禁”三种状态。

不得把计划项表述为当前能力。

### 历史决策

只有用户明确询问演进原因、旧原型或历史方案时才检索 `archive/`。引用时必须写明日期或版本，并说明其不代表当前实现。

## 4. 文档职责

每个事实只设一个主权威，其余文档用链接引用，不复制整段规范。

| 信息                                      | 唯一主权威                  |
| ----------------------------------------- | --------------------------- |
| 功能 ID、优先级、产品完成条件             | `current/产品与功能基线.md` |
| 中文、布局、滚动、焦点、IME、可访问性     | `current/设计与交互基线.md` |
| 领域契约、协议、源码和测试位置            | `current/实现与代码映射.md` |
| 测试层级、矩阵、候选和发布门禁            | `current/测试与验收基线.md` |
| 版本状态、提交、VSIX 和 accepted evidence | 对应版本 `manifest.json`    |
| 某版本的目标、阶段、范围与已知问题        | 对应版本 `README.md`        |
| 历史原型、旧规格和迁移过程                | `archive/` 对应目录         |

## 5. 写作与命名规范

### 文件命名

- 当前基线使用稳定中文名称，不带日期和版本号。
- 版本目录固定为 `releases/vX.Y.Z/`。
- 历史资料按 `archive/<类型>/<版本或日期>/` 归档。
- 禁止 `最终版`、`最新版`、`new`、`copy`、`备份`、`xxx-pass-results` 等无法长期判断身份的名称。

### 文档开头

current 和版本计划应在标题后声明：

- 文档身份或状态；
- 适用范围；
- 不包含的内容；
- 相关主权威链接。

### 内容规则

- 使用稳定标题和功能 ID，避免用临时行号或截图名称作为唯一定位方式。
- 代码路径、命令、协议字段和配置键保持原文。
- 当前事实与未来计划分开书写。
- 测试数量、产物大小和通过结论必须绑定提交或 evidence，不复制成长期基线。
- 原型只能解释历史设计，不能作为当前实现或验收证据。
- 删除或移动文件前，先修复全部入链，并运行文档校验。

## 6. 维护规则

1. 行为、源码路径、测试映射或证据路径变化时同步更新对应主权威。
2. 已发布 `releases/vX.Y.Z/` 不可修改；勘误通过新版本或外部勘误记录处理。
3. draft 版本可以重写，但必须同步 README、manifest、版本索引和 `catalog.json`。
4. archive 只保留独特历史信息；字节级重复、临时脚本和系统生成物应删除。
5. 普通测试写入 `.validation/evidence`；只有显式发布任务可写发布证据。
6. 所有文档改动执行：

```bash
npm run docs:verify
```

`docs:verify` 必须验证本地链接、版本 manifest、released evidence 和 `catalog.json` 的规范入口。
