## 2. V003-CR-01：属性冲突未进入安全规则

### 问题位置

- `src/commit/commitSelectionRuleEvaluator.ts`
- `createCommitSelectionEvaluator().evaluate()`

### 现状与触发条件

规则评估器只在 `input.status` 上检查 `conflicted`、`obstructed` 和 `incomplete`，没有对独立的 `input.propStatus` 执行同等安全检查。

例如：

```text
status=modified
propStatus=conflicted
```

当路径规则未命中时，该候选会按 `modified` 状态策略得到“推荐提交”，`safetyLocked` 为 `false`。如果配置了更宽的推荐路径规则，`status=normal` 且 `propStatus=conflicted` 也可能被放行。

### 影响

- 违反“安全规则优先于路径规则与状态策略”的领域契约。
- 违反 `conflicted` 不可配置、不可被 AI 或本地规则覆盖的验收标准。
- 提交页、SCM、Changelist 和 AI 请求会共享这个错误本地结论。

### 修复要求

- 在任何路径规则或可配置状态策略之前，同时检查 `status` 和 `propStatus` 的阻止状态。
- 安全结果必须返回 `decision=blocked`、`reasonKey=safetyBlocked` 和 `safetyLocked=true`。
- 修复不得使 `status=normal` 且 `propStatus=modified` 的仅属性变化回退到普通 `normal` 策略。

### 最低回归测试

- `modified + conflicted` 始终阻止。
- `normal + conflicted` 始终阻止，即使存在推荐路径规则。
- `conflicted + modified` 保持阻止。
- AI 不能将上述候选改为推荐。

## 3. V003-CR-02：仅 SVN 属性变化无法生成提交计划

### 问题位置

- `src/commit/commitPlanBuilder.ts`
- `getBlockedCommitReason()` 与 `isCommittableStatus()`

### 现状与复现

`v0.0.3` 规则评估器已将以下组合判定为 `propertyModified` 并默认推荐：

```text
status=normal
propStatus=modified
```

但提交计划构建器仍只调用 `isCommittableStatus(candidate.status)`，`normal` 不在可提交状态集合中。实际运行结果为：

- `commitPaths` 为空。
- `canCommit=false`。
- 问题文案为“当前 SVN 状态 normal 不支持直接提交。”

### 影响

- 设置预览和提交页会显示“推荐提交”，但提交前检查一定失败。
- `v0.0.3` 修正仅属性变化的核心目标在最终提交链路中未实现。
- 现有评估器单元测试只证明“分类为推荐”，未证明“可进入提交计划”。

### 修复要求

- 提交可行性判断必须使用 `(status, propStatus)` 二元组或已验证的候选决策，不能只检查文本状态。
- `normal + modified` 应进入 `commitPaths`，但不应进入 `addPaths` 或 `removePaths`。
- 属性冲突、路径阻塞和状态不完整仍必须优先阻止。

### 最低回归测试

- 仅属性变化候选从规则评估、候选采集到 `buildCommitPlanPreview()` 的集成测试。
- 断言 `commitPaths` 包含该路径、`addPaths` 与 `removePaths` 不包含该路径、`canCommit=true`。
- 覆盖提交预览和执行前状态复验。

## 4. V003-CR-03：损坏配置在保存时被重建

### 问题位置

- `src/commit/commitSelectionRuleService.ts`
- `src/config/svnWorkbenchConfig.ts`
- `CommitSelectionRuleService.saveRepositoryRules()`

### 现状与触发条件

`readSvnWorkbenchConfig()` 读取非法 JSON 或非对象顶层时，返回 `exists=true`、`raw=undefined` 和解析警告。`saveRepositoryRules()` 未拒绝该状态，继续调用 `updateSvnWorkbenchConfig()`。后者会从空对象重建配置并写回文件。

因此，用户在设置页保存提交选择规则时，可能丢失以下内容：

- `commitConvention`。
- `commitCandidateFilterPresets`。
- 未识别的团队配置字段。
- 尚未被当前版本识别的前向兼容数据。

### 影响

- 违反“保存一个设置区域时保留其他配置和未知字段”的配置契约。
- 违反“不得将损坏配置静默保存为空配置”的 `v0.0.3` 验收要求。
- 保存结果虽可返回警告，但数据已被覆盖，无法依靠事后提示恢复。

### 修复要求

- 文件存在但 JSON 解析失败、顶层不是对象或读取失败时，保存必须被拒绝。
- 拒绝后原文件必须保持字节不变，界面应提示用户先打开并修复配置。
- 配置文件合法时，仍只更新 `commitSelection` 顶层键，保留其他顶层键和 `commitSelection` 内部未知字段。
- 如需提供“重建文件”能力，必须作为独立、明确警告数据损失的用户操作，不得复用普通保存。

### 最低回归测试

- 非法 JSON 保存失败，原始内容不变。
- 数组、字符串或 `null` 顶层保存失败，原始内容不变。
- 文件读取失败时不执行写入。
- 合法文件只更新 `commitSelection`，其他顶层键和未知字段保持不变。
- 设置页显示可恢复的中文错误和“打开 `.svn-workbench.json`”动作。

## 5. V003-CR-04：无效 AI 结构被当成成功结果

### 问题位置

- `src/ai/openAiCompatibleProvider.ts`
- `src/ai/aiResultValidator.ts`
- `parseJsonResult()` 与 `normalizeAiSelectionResult()`

### 现状与触发条件

AI 提交选择响应只要是可解析的 JSON 对象，即使缺失 `recommended`、`excluded`、`needsReview` 和 `blocked` 列表，也会被规范化为四个空数组。字段类型错误时也会被静默转换为空数组。

例如以下响应会被当成配置模型的成功结果：

```json
{}
```

Controller 随后使用空的 `recommended` 列表覆盖 `state.selectedPaths`，造成用户当前提交选择被静默清空，而界面仍显示外部模型调用成功。

### 影响

- 违反“AI 结果结构无效时保留当前选择并继续本地流程”的降级契约。
- 用户可能在没有明确操作的情况下丢失已人工确认的提交篮。
- 结果分类之间的重复路径也未被拒绝，同一候选可同时出现在推荐与阻止结果中。

### 修复要求

- 在规范化之前严格验证四个分类字段均存在且为数组。
- 每个条目必须具有非空 `path` 和可处理的 `reason`；路径规范化、仓库范围和候选集合校验继续在 Host 边界执行。
- 同一路径不得在多个决策分类中重复出现。
- 无效结果必须抛出结构化错误，进入 `local-rule-fallback` 或等价降级流程，保留当前选择和预览。
- 界面必须如实显示 AI 失败原因，不得将空规范化结果表述为模型分析成功。

### 最低回归测试

- `{}`、缺失分类字段、分类字段非数组时进入失败降级。
- 条目缺失路径、路径为空或同一路径跨分类重复时拒绝结果。
- 无效结果不修改 `selectedPaths`、已有提交预览和人工勾选。
- 设置模型返回合法结果时，范围校验、本地安全边界与过期绑定仍正常生效。

## 6. 修复顺序建议

1. 先修复 V003-CR-01，将 `(status, propStatus)` 的安全检查收口。
2. 再修复 V003-CR-02，让提交计划复用同一二元状态契约。
3. 修复 V003-CR-03，先阻止可能破坏团队配置的保存路径。
4. 修复 V003-CR-04，将 AI 响应结构错误纳入现有失败降级。
5. 执行相关单元、组件、Extension Host 和真实 SVN 回归，再进入完整门禁。

V003-CR-01 与 V003-CR-02 应作为同一条状态契约修复评审：前者确保安全状态不被放行，后者确保合法的属性变化可进入提交链路。

## 7. 关闭条件

每个问题关闭前必须同时满足：

- 根因已修复，不是仅在 UI 层隐藏错误或改写提示。
- 新增与问题一一对应的自动化回归测试。
- 不降低安全校验、不删除断言、不通过批量更新基线规避失败。
- `npm run check` 和直接相关测试通过。
- 最终候选交付前 `npm run verify` 通过。
- 修复后同步更新本文状态和 `docs/current/` 对应映射，并执行 `npm run docs:verify`。
