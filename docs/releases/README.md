### v0.1.x AI 执行协议

1. AI 开始任一版本前，必须完整阅读根 `README.md`、`docs/README.md`、`docs/current/README.md`、四份 current 基线、当前版本 README、直接前置版本 README，以及本路线来源报告。
2. 每次只允许一个版本处于 `developing`；前一版本未满足退出门禁时，后一版本保持 `planned`，不得提前把依赖未完成的行为接入生产路径。
3. 每个版本先完成只读调研与 fixture/baseline，再按“纯领域逻辑 → 适配层 → Host/协议 → Svelte → Mock/守卫 → 测试 → current 文档”顺序实施；不需要协议变化时明确写明“不改协议”。
4. 代码改动不得降低 `moduleId + taskId + operationScope`、scope/token/revision、路径、草稿、AI 外发和写操作复验契约；组件回调不成为安全权威。
5. 普通实现至少运行 `npm run check` 和直接相关测试；版本候选前运行 `npm run verify`。只有用户明确要求发布时才运行 `npm run evidence:release`、生成 VSIX 指纹、创建标签或把 manifest 改为 `candidate/released`。
6. 每个版本必须给出一个用户可独立体验的主路径、正常/空/失败/过期/恢复分支、可回退方式和明确延期项；不得以“后续版本会补齐”为由交付不可用的半成品。
7. AI 完成任务时必须同步更新对应 current 基线与实现/测试映射，并如实列出实际运行的命令、未运行项和剩余风险；历史发布记录不可改写。

## 规划治理

- 每个版本进入实现前，先按该版本的具体交互问题进行一次开源作品研究；候选广搜后只深入 2～3 个真实源码、Issue 或失败案例可核对的方案；
- 外部参考只帮助比较交互和实现取舍，不能覆盖本项目的 SVN scope、安全确认、多根工作区和本地降级约束；
- 每个版本必须有一个可由用户独立体验的主路径和明确的延期项，不能因后续版本存在而以“半成品底座”通过；
- P0 版本按顺序实施；P1 / P2 只有在依赖的候选验收通过后进入开发，不以文档已存在视为依赖完成。
